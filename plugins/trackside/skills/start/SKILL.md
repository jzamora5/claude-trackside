---
name: start
description: Bind this chat to a track (the user may call a track a workspace) and load its state, create a new track, or unbind the chat. Run it when the user types /trackside:start, asks to work on a track or agrees to one you suggested, or when the work an unbound chat starts clearly fits one track. Never create a track, or bind a chat to a track that only might fit, without the user agreeing.
allowed-tools: Bash(bash "${CLAUDE_SKILL_DIR}/../../scripts/bind.sh" *) Bash(bash "${CLAUDE_SKILL_DIR}/../../scripts/audit.sh" *) Bash(bash "${CLAUDE_SKILL_DIR}/../../scripts/status.sh" *) Bash(bash "${CLAUDE_SKILL_DIR}/../../scripts/freshness.sh" *) Bash(bash "${CLAUDE_SKILL_DIR}/../../scripts/setup-git.sh" *)
---
If `${CLAUDE_PROJECT_DIR}` has no `.trackside/` folder, which happens when a chat moves to another folder after it starts, use the nearest folder at or above the current one that has a `.trackside/` wherever this says `${CLAUDE_PROJECT_DIR}`.

Run each command below exactly as written, one per call, apart from that folder when it applies: trackside pre-approves them in that form, so they run without permission prompts.

Arguments: $ARGUMENTS

The trackside folder is `${CLAUDE_PROJECT_DIR}/.trackside/`. Each feature is a folder in it, and each track is a folder in its feature. The first word of the arguments is the track's full name, `<feature>/<track>`; a bare track or feature name doesn't count. Anything after it is the user's request.

To bind the chat: `bash "${CLAUDE_SKILL_DIR}/../../scripts/bind.sh" "${CLAUDE_PROJECT_DIR}" "${CLAUDE_SESSION_ID}" "<name>"`. It prints the track it bound, or why it couldn't, and a note when trackside's hooks can't run; pass any note on to the user.
- If it says the chat has unsaved work on another track, run `/trackside:save` for that track first, then bind again. If the user says that work doesn't belong to that track, unbind first instead.
- `off` as the name unbinds the chat. Tell the user if its work since the last save wasn't saved, and stop there.

**If no name was given, or it isn't a track's full name:**
1. List the tracks, their current work or goal, and the command that starts each: `bash "${CLAUDE_SKILL_DIR}/../../scripts/status.sh" "${CLAUDE_PROJECT_DIR}"`. If a bare name was given, say which full names it could mean.
2. Ask which one to use. Once the user picks one, bind it and continue under "Once bound".
3. If none fits, propose a new track in one message, and create nothing until the user confirms or corrects it:
   - Its name, `<feature>/<track>`, in an existing feature when one fits. Use short, lowercase, hyphenated words named after the product or topic, so the name is easy to guess (for example `checkout/discounts`), not ticket keys. Names start with a letter or digit and use only letters, digits, `.`, `_` and `-`. A track can't be named `off`.
   - Its goal, from what the user said.
   - Whether each item starts clean, in those words: yes when the work is a stream of separate items that don't build on each other, such as pull request reviews or answering support questions, so only the track's rules and lessons carry over from one item to the next; no for work that builds on its history, such as a feature, research or docs.
   - For a new feature, its FEATURE.md values, filled in from what you can find instead of asked one by one: repos (the ones this work involves, picked from the git folders that `find "${CLAUDE_PROJECT_DIR}" -maxdepth 2 -name .git -not -path "*/.claude/*"` finds, relative to the project root, `.` for the root itself; ask when it isn't clear), source docs (only the ones the user named, otherwise "none yet"), decisions (`DECISIONS.md` in the feature folder, unless the user named a source doc section for them), and planning (`openspec` if `${CLAUDE_PROJECT_DIR}/openspec/` exists, otherwise none). Never guess a goal or a source doc.
   - If `${CLAUDE_PROJECT_DIR}/.trackside/` doesn't exist yet, also offer two separate choices: keeping `.trackside/` out of the project's git, when the project is a git repo, so the state isn't committed with the code; and giving `.trackside/` its own history, which trackside then commits to as it saves.
4. Once the user confirms, copy the templates from `${CLAUDE_SKILL_DIR}/../../templates/` and fill them in: `FEATURE.md` (plus `DECISIONS.md` when decisions go there) into `${CLAUDE_PROJECT_DIR}/.trackside/<feature>/` for a new feature, and `CONTEXT.md`, `STATE.md` and `NOTES.md` into `${CLAUDE_PROJECT_DIR}/.trackside/<feature>/<track>/`, plus `LESSONS.md` when each item starts clean. Delete any template line you can't fill instead of leaving its placeholder. For the git choices the user accepted, run `bash "${CLAUDE_SKILL_DIR}/../../scripts/setup-git.sh" "${CLAUDE_PROJECT_DIR}"` followed by `ignore`, `history` or both. Then bind it and continue under "Once bound".

**Once bound:**
1. Read `${CLAUDE_PROJECT_DIR}/.trackside/<feature>/FEATURE.md`, then the track's `CONTEXT.md`, its `LESSONS.md` when `CONTEXT.md` says each item starts clean, and `STATE.md` (Inbox first), then every file the first two list under "Read on start". If one doesn't exist yet, say so and continue. If FEATURE.md names source docs and there's no `DIGEST.md` yet, suggest `/trackside:digest <feature>` once, in the three-line reply of step 5, and only when the user asked for nothing else.
2. Check what changed since the state was written: `bash "${CLAUDE_SKILL_DIR}/../../scripts/freshness.sh" "${CLAUDE_PROJECT_DIR}" "<feature>/<track>" "$PWD"`. Treat what STATE.md says about those repos as unconfirmed until you've checked it. Then run trackside's check of the track: `bash "${CLAUDE_SKILL_DIR}/../../scripts/audit.sh" "${CLAUDE_PROJECT_DIR}" "<feature>/<track>" start`. Fix the issues it lists that only move or de-duplicate text, or fill in what's missing, in your first save; mention the ones that need the user once in this chat, at a natural pause, never before answering what they asked. Then run `bash "${CLAUDE_SKILL_DIR}/../../scripts/audit.sh" "${CLAUDE_PROJECT_DIR}" "<feature>/<track>" due`: if it prints `due`, start the trackside audit skill for the track; it runs in the background on a cheaper model. When its list comes back, apply the items it marks lossless, write the other items to the track's `review-<date>.md` (or "Nothing needs the user."; writing the file marks the review as handled) with an Inbox line pointing to it when it has items, commit the trackside folder if it's its own git repo, and show the user the other items once, at a natural pause.
3. For the rest of this chat, work only within this track. Keep its STATE.md current, and record each decision as soon as it's made, where FEATURE.md says decisions go; a hook reminds you after edits and research. Write down only what a new chat couldn't get from the code, git, the docs or a command: no copied file contents, diffs or test output; point to them instead. Update STATE.md before you write a reply, not after it, and keep the bookkeeping out of your replies: don't tell the user about saves, fixes the automatic check asked for, or commits of the trackside folder. Mention trackside only when the user has to decide something, in a line before the rest of your reply, never after a question you ask. If FEATURE.md names source docs, they're the source of truth: before you state, decide or change anything they cover, read it with the lookup skill (`/trackside:lookup <ID or heading words>`), which prints the exact text, instead of relying on what STATE.md says about them.
4. If this chat already had work in it before the binding, offer to run `/trackside:save` now, so what the chat already knows reaches the track instead of only what happens next.
5. If you bound the chat on your own, without the user typing `/trackside:start` or asking for this track, start your reply with one line naming the track and saying that `/trackside:start off` undoes it. When `CONTEXT.md` says each item starts clean, say so in your first line too. If the user asked for something that isn't done yet, after the name or in the message that led to this track, carry on with it. A ticket still starts the way `/trackside:next` does: propose it with its plan, and write no code until the user approves. Otherwise reply with three lines: where things stand, what's in the Inbox and what changed in the repos, and the suggested next step. Then wait.
